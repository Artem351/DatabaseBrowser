## Основа и договорённости

1. Предпочтительно начать от `main` после слияния реализации подключений. Если слияние задерживается, создать ветку UC-06 от ветки подключений и временно направить PR в неё. После слияния обновить базовую ветку и проверить diff.
2. Подключения, их профили и жизненный цикл остаются ответственностью модуля подключений. Модуль индексов получает уже открытое соединение и не закрывает его.
3. Все обращения к пользовательской БД выполнять через `ConnectionController.submit_database_operation(name, operation)`. Внутри worker доступен `manager.executor.connection`. В интерфейс передавать обычные данные, без соединений и курсоров.
4. Для индексов использовать отдельные файлы в `src/database_browser/schema/`. Изменения общего `ui.py` ограничить подключением вкладки Schema. Согласовать с командой владельца этой вкладки, поскольку позже к ней добавятся Tables, Views и Export.
5. Сохранить существующую схему хранения профилей: отдельная `settings.sqlite3` в пользовательской папке приложения. Для индексов дополнительное хранилище не нужно.
6. Сохранить согласованные зависимости: Python 3.14.x, PyQt6 6.12.0, PyQt6-Qt6 6.12.0, PyQt6-sip 13.13.0, pytest 8.4.2, pytest-qt 4.5.0. Локальные requirements совпадают по строкам с веткой подключений. Отдельный пакет sqlite3 не устанавливается.

В ветке подключений `pyproject.toml` допускает Python >=3.12 и более широкий диапазон PyQt6; для нашей проверки использовать именно закреплённые версии requirements. Изменение общей политики поддержки Python согласовать отдельно.

## Устройство модуля

Предлагаемая структура согласуется с разделением UI / Service / Repository на диаграмме классов Vision:

```text
src/database_browser/schema/
    __init__.py
    models.py          # Index, столбцы индекса, сведения о таблицах
    repositories.py    # IIndexRepository и SQLiteIndexRepository
    services.py        # SchemaManager: операции с индексами
    ui.py              # SchemaTab и общая форма создания/изменения
tests/
    test_indexes.py    # интеграционные проверки на временных SQLite-файлах
    test_indexes_ui.py # формы и взаимодействие с настоящим worker
```

Имена и границы уточнять по актуальной основе перед кодированием. Новые СУБД и универсальный плагинный механизм сейчас не реализовывать; интерфейс репозитория отделяет SQLite от логики сценариев.

Модель индекса должна хранить имя, таблицу, упорядоченные ключевые столбцы, UNIQUE, происхождение и исходное SQL-определение. Для макета редактора также нужны направления ASC/DESC. Сведения читать из `sqlite_schema` и PRAGMA, а не разбирать произвольный SQL регулярными выражениями.

## Этап 1. UC-06 — создать индекс

По уточнению пользователя: сначала код этапа, затем тесты и исправления. К следующему UC переходить после успешной проверки предыдущего.

- Читать список пользовательских таблиц, доступных столбцов и индексов.
- Включить вкладку Schema с разделом Indexes: список, сведения о выбранном индексе, кнопка создания и обновление списка.
- Сделать форму: таблица, имя индекса, выбор одного или нескольких столбцов, их порядок, ASC/DESC, UNIQUE, предпросмотр DDL, сохранение и отмена.
- Проверять непустое имя, выбранные столбцы и их существование. Имена таблиц, столбцов и индексов корректно заключать в кавычки; значения в запросах метаданных параметризовать.
- Создавать индекс в worker, после успеха перечитывать схему и выбирать созданный объект.
- При ошибке сохранять введённые данные и показывать причину без завершения приложения.

Проверки:

- обычный, составной и UNIQUE-индекс действительно появились в SQLite;
- порядок столбцов и ASC/DESC соответствуют форме;
- занятое имя, отсутствующая таблица/столбец, пустые обязательные поля;
- дубликаты мешают UNIQUE, несколько NULL допустимы по правилам SQLite;
- имена с пробелами, кавычками и ключевыми словами;
- отмена формы не меняет схему;
- без подключения / без таблиц / только чтение действия доступны корректно;
- после создания список обновлён, ошибка видна в UI, приложение продолжает работать.

Результат: самостоятельный PR UC-06 с работающим интерфейсом и тестами.

## Этап 2. UC-08 — удалить индекс

- Для выбранного индекса показывать имя связанной таблицы и запрашивать подтверждение.
- Удалять только пользовательские индексы. Индексы PRIMARY KEY и UNIQUE-ограничений защищать и на уровне логики, и в интерфейсе; объяснять необходимость UC-04.
- Пользовательский UNIQUE-индекс разрешено удалить: UNIQUE сам по себе не означает принадлежность ограничению таблицы.
- После успеха перечитывать список; при ошибке показывать причину и фактическое состояние схемы.

Проверки:

- обычный и пользовательский UNIQUE-индекс удалены;
- таблица и все её строки остались;
- отмена сохраняет индекс;
- защищены индексы UNIQUE-ограничений и PRIMARY KEY, для которого SQLite действительно создаёт индекс;
- ошибка SQLite, отсутствующий индекс и режим только чтения обработаны;
- диалог содержит связанную таблицу, список обновлён после подтверждения.

Результат: отдельный PR UC-08 поверх UC-06.

## Этап 3. UC-07 — изменить индекс

- Открывать общую форму с текущими параметрами индекса.
- В рамках текстового UC-07 менять столбцы и UNIQUE; имя и таблицу существующего индекса сохранить. Переименование не включать без отдельной договорённости.
- Проверять определение до изменения, затем выполнять замену в одном SAVEPOINT: DROP старого → CREATE нового → RELEASE.
- При ошибке выполнять ROLLBACK TO и RELEASE, сохраняя старый индекс. Не применять общий commit/rollback к чужой транзакции и не использовать executescript для замены.
- Защитить индексы ограничений тем же правилом, что в UC-08.
- После операции показывать фактическое определение. При внешней незавершённой транзакции не сообщать о гарантированной записи на диск до её COMMIT.

Проверки:

- изменение набора и порядка столбцов, ASC/DESC;
- включение и отключение UNIQUE;
- ошибка из-за дубликатов восстанавливает прежний SQL, метаданные и поведение индекса;
- ошибка создания после DROP не оставляет БД без прежнего индекса;
- отмена и запрет изменения индекса ограничения;
- успешная и неудачная замена не фиксируют и не откатывают внешние изменения данных;
- без внешней транзакции успешная операция сохраняется после закрытия и повторного открытия БД;
- после неудачной операции соединение остаётся пригодным для дальнейшей работы.

Предложение для первой версии формы: создавать и изменять индексы на именованных столбцах. Существующие partial/expression-индексы и определения с неподдерживаемой COLLATE показывать с исходным SQL, но не переписывать упрощённой формой с потерей WHERE, выражений или правил сравнения. Это ограничение явно описать в README и сообщении интерфейса. Удаление пользовательских индексов таких видов можно поддержать без разбора их определения.

Результат: отдельный PR UC-07 поверх UC-08.

## Общие проверки интеграции

- После переключения БД очищать прежние объекты и загружать новую схему; не показывать список предыдущего подключения.
- На время операции блокировать повторное действие; при read-only оставлять просмотр и блокировать изменение.
- Учесть, что существующий `connection_changed` испускается после каждой операции, включая чтение схемы. Не запускать на нём безусловное обновление: иначе возникает цикл запросов. Загрузку после изменения подключения запускать после освобождения worker с проверкой контекста.
- Сигнал `error_occurred` сейчас обрабатывается DatabaseTab. Организовать единственный показ ошибки и сообщение в нужной вкладке без дублирующих диалогов.
- Изменения схемы выполнять атомарно и не затрагивать чужую транзакцию. Ошибку обновления списка после успешной записи отличать от ошибки самой записи.
- Ошибки проверять на реальной SQLite: read-only через URI mode=ro, ограничения и откаты на настоящих данных. Искусственные сбои использовать дополнительно там, где требуется отказ в конкретный момент.
- Для GUI использовать pytest-qt и ожидание сигналов, без произвольных задержек.
- Перед каждым PR запускать весь актуальный набор тестов, включая подключения, и `pip check`.
- На Windows вручную пройти создание, удаление, успешную замену и неудачную замену UNIQUE на демонстрационной БД.

Критерий готовности каждого UC: доступен весь путь пользователя, есть отмена и понятные ошибки, UI отражает фактическую схему, автоматические проверки пройдены, README и описание PR обновлены.

## Проверенные основания

- [SAVEPOINT, RELEASE и ROLLBACK TO](https://www.sqlite.org/lang_savepoint.html): вложенная операция может быть отменена без общего отката внешней транзакции.
- [PRAGMA index_list и index_xinfo](https://www.sqlite.org/pragma.html#pragma_index_list): происхождение индекса и состав его ключа.
- [CREATE INDEX](https://www.sqlite.org/lang_createindex.html): UNIQUE, NULL, порядок и дополнительные варианты определения.

Во время подготовки плана на локальном SQLite 3.50.4 выполнен небольшой эксперимент: неудачная замена индекса на UNIQUE через SAVEPOINT восстановила прежний индекс и сохранила внешнюю транзакцию. Это проверка подхода, не готовые тесты приложения. Тесты ветки подключений и установка согласованного набора зависимостей здесь ещё не выполнялись.
